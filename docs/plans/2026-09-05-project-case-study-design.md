# 프로젝트 케이스 스터디 상세 화면 설계

## 목표

Finder 기반 프로젝트 탐색과 기존 외부 링크 동작은 유지하면서, 각 프로젝트 상세를 채용 담당자가 한 번의 스크롤로 읽을 수 있는 케이스 스터디로 바꾼다. 첨부 이미지는 정보 구조 참고로만 사용하며 이미지 안의 회사명, 수치, 프로젝트 내용은 가져오지 않는다.

## 검토한 방식

1. **단일 스크롤 케이스 스터디 — 채택**: 기간·제목, 링크, 기술, 아키텍처/핵심 포인트, 문제 해결 서사를 순서대로 읽는다. Finder의 좁은 창과 모바일에서도 정보가 숨지 않고 검색·복사·접근성이 좋다.
2. **왼쪽 메타데이터 + 오른쪽 본문 2열**: 큰 화면의 스캔은 빠르지만 기존 Finder 사이드바와 함께 쓰면 본문 폭이 부족하다.
3. **슬라이드/캐러셀**: 발표 자료와 비슷하지만 전체 내용을 비교하기 어렵고 키보드·스크린리더·모바일 탐색 비용이 커진다.

## 정보 구조

상세 화면은 `연도/기간과 타이틀 → 기존 스토어·외부 링크 → #기술 태그 → 시스템 아키텍처 또는 핵심 포인트 → 업무·문제·원인·측정·해결·평가·비고` 순서다. 아키텍처는 별도 이미지가 없어도 접근 가능한 텍스트 노드 흐름으로 표현한다. 서사는 enum 기반 항목 목록으로 저장해 값이 있는 항목만 정해진 순서로 렌더링하고, `description`은 기존 호환성을 위한 요약으로 남긴다.

실제 저장소에는 PersonaChat 설계 문서를 제외하면 문제·원인·측정·평가의 근거가 없다. 따라서 새 필드는 선택형으로 만들고 임의 성과나 수치를 생성하지 않는다. 기존 프로젝트에는 검증 가능한 업무와 공개 링크 기반 핵심 포인트만 넣고, 상세 회고가 없는 항목은 숨긴다.

## 반응형·접근성

상세 내부의 실제 가용 폭을 기준으로 데스크톱에서는 `라벨 | 본문`, 좁은 화면에서는 `라벨` 위에 `본문`을 배치한다. 아키텍처 노드는 넓은 화면에서 가로, 좁은 화면에서 세로 흐름으로 전환한다. 링크 버튼의 기존 키, 요청 중 비활성화, 중복 차단, 성공·실패 live-region 피드백을 그대로 보존한다. 기술 태그는 버튼처럼 보이지 않는 `#태그`로 표시하고, 200% 글자 확대에서도 가로 오버플로가 없어야 한다.
